## 1. О документе

Этот документ — самостоятельная тема, не привязанная конкретно к Zynq: обычная сборка `.apk`-пакетов Alpine под архитектуры **armv7** (основной вариант в README.md) и **armhf** (полностью аналогично, отличается только имя архитектуры). Пригодится, когда нужной программы нет в `main`/`community`, либо нужна своя версия/патч существующего пакета.

Сборка выполняется на x86_64-хосте через тот же механизм chroot + qemu-user-static, что уже настроен в README.md (раздел 8) — вся новая инфраструктура здесь сводится к одному дополнительному пакету (`alpine-sdk`) поверх уже знакомого окружения.

## 2. Как устроена система пакетов Alpine

- **`apk`** — сам пакетный менеджер: ставит `.apk`, знает про репозитории, подписи, зависимости. С ним уже работали в README.md (`apk add`, `apk update`).
- **`abuild`** — инструмент **сборки** пакета из исходников по рецепту `APKBUILD` (аналог `dpkg-buildpackage` у Debian, `makepkg` у Arch, `ebuild` у Gentoo).
- **`aports`** — git-репозиторий, где Alpine хранит APKBUILD-рецепты всех официальных пакетов (`main`, `community`, `testing`): https://gitlab.alpinelinux.org/alpine/aports. Свой пакет оформляется точно так же, просто в собственном каталоге — не обязательно быть частью официального aports.
- **`APKBUILD`** — сам файл-рецепт: shell-скрипт с определённым набором переменных и функций.
- **`alpine-sdk`** — метапакет, который ставит `abuild` и сопутствующие инструменты одной командой.

## 3. Подготовка окружения для сборки

`abuild` должен работать от **обычного пользователя**, а не root — так безопаснее, поскольку сборочные скрипты сторонних пакетов выполняют произвольный код; пользователь должен состоять в группе `abuild`.

Проще всего переиспользовать уже готовый armv7-chroot (README.md, разделы 6–8). Для чистоты можно завести отдельный такой же chroot специально под сборку — чтобы не тащить компиляторы и dev-заголовки в продакшен-rootfs; процедура бутстрапа при этом идентична README.md §6/§7, менять нечего.

```bash
sudo chroot "$BUILDROOT" /bin/sh
```

Внутри chroot (ещё от root — на этом шаге нужны права на `adduser`/`apk add`):

```sh
apk add alpine-sdk sudo
echo 'builder ALL=(ALL) NOPASSWD: ALL' >> /etc/sudoers
adduser -D builder
addgroup builder abuild
su - builder
```

Дальше всё — уже от имени `builder`. Один раз сгенерировать ключ подписи:

```sh
abuild-keygen -a -i
```

`-a` добавляет публичный ключ в `/etc/apk/keys` этой же chroot-системы (значит, она сразу сможет доверять пакетам, подписанным этим ключом), `-i` прописывает приватный ключ в `~/.abuild/abuild.conf` (переменная `PACKAGER_PRIVKEY`).

> Если позже понадобится собирать ещё и на настоящем ARM-железе (не в эмуляции) — тот же приватный ключ (`~/.abuild/*.rsa`) стоит скопировать и туда, чтобы пакеты с разных машин были подписаны одним и тем же ключом.

## 4. Анатомия APKBUILD

Минимальный, но полный пример — тот же `hello.c`, что и в README.md §15.2, только теперь оформленный как настоящий `.apk`-пакет вместо разовой ручной установки файла:

```sh
# Contributor: Ваше Имя <you@example.com>
# Maintainer: Ваше Имя <you@example.com>
pkgname=hello-zynq
pkgver=1.0
pkgrel=0
pkgdesc="Тестовая программа для Zynq-7010"
url="https://example.com/"
arch="all"
license="MIT"
depends=""
makedepends=""
subpackages=""
source="hello.c"
builddir="$srcdir"

build() {
	cd "$builddir"
	${CC:-cc} -O2 -o hello hello.c
}

check() {
	cd "$builddir"
	./hello
}

package() {
	cd "$builddir"
	install -Dm755 hello "$pkgdir"/usr/local/bin/hello
}

sha512sums="3737cc8fec6196e5f8246fee020d49e8e9cd60a28c2f6937387557ff1502c01ae1e9b6cc14b57e4bf7bdc9097f1024cfa831f315ae623a5e43a1d35532a7360c  hello.c"
```

Разбор ключевых полей:

| Поле/функция | Назначение |
|---|---|
| `pkgname`, `pkgver`, `pkgrel` | Имя, версия, номер пересборки (увеличивайте `pkgrel`, если меняли APKBUILD без смены `pkgver`) |
| `arch` | `all` — рецепт можно собрать под любую архитектуру (каждый раз получится свой arch-специфичный `.apk`, это не «универсальный бинарник»); `noarch` — по-настоящему не зависящий от архитектуры контент (скрипты, данные); либо явный список `"armv7 armhf aarch64"` |
| `depends` | Зависимости времени выполнения — ставятся вместе с пакетом на целевой машине |
| `makedepends` | Зависимости только для сборки, в готовый пакет не попадают |
| `source` | Список источников: URL, либо, как в примере, просто имя локального файла рядом с APKBUILD (раз имя не похоже на URL — abuild берёт файл локально, не пытаясь скачать) |
| `build()` | Компиляция; рабочий каталог — `$builddir` (для архивов обычно `$srcdir/<имя-версия>` после распаковки) |
| `check()` | Тесты (опционально; пропускаются при `abuild -r -k`, если сборка ещё не готова к тестам) |
| `package()` | Раскладка готовых файлов в `$pkgdir` — именно это содержимое попадёт в `.apk` |
| `sha512sums` | Контрольные суммы всех файлов из `source=`; на практике заполняются автоматически командой `abuild checksum`, а не руками |

## 5. Первый пакет: от newapkbuild до готового .apk

Каркас удобнее не писать руками, а сгенерировать `newapkbuild`:

```sh
mkdir -p ~/aports-local/hello-zynq && cd ~/aports-local/hello-zynq
cp /path/to/hello.c .
newapkbuild -n hello-zynq -d "Тестовая программа для Zynq-7010" hello-zynq-1.0
```

`newapkbuild` создаст шаблон `APKBUILD` — отредактируйте его по образцу раздела 4; `build()`/`package()` под конкретную программу почти всегда приходится дописывать руками, автогенерация закрывает только каркас (а для типовых систем сборки есть готовые шаблоны — `newapkbuild -a` для autotools, `-C` для CMake, `-m` для meson, `-y` для python, `-r` для rust).

Дальше — пересчитать контрольные суммы и собрать:

```sh
abuild checksum
abuild -r
```

`abuild checksum` сам допишет актуальный `sha512sums=` в APKBUILD (руками, как в примере раздела 4, считать не нужно — там суммы даны только для наглядности). `abuild -r` собирает пакет и при необходимости сам доустанавливает недостающие `makedepends` через `sudo apk add`.

Готовый файл окажется в `~/packages/<репозиторий>/<arch>/hello-zynq-1.0-r0.apk` — имя репозитория берётся из каталога верхнего уровня (в примере — `aports-local`), путь настраивается переменной `REPODEST` в `~/.abuild/abuild.conf` или `/etc/abuild.conf`.

## 6. Кросс-архитектурная сборка: armv7/armhf на x86_64-хосте

Если разделы 3–5 выполнялись **внутри** armv7-chroot (как и рекомендовано) — всё уже собралось под правильную архитектуру, отдельно ничего делать не нужно: `apk --print-arch` внутри такого chroot и так вернёт `armv7`, и `abuild` соберёт пакет «нативно» с точки зрения инструментов — хотя физически всё выполняется под qemu-эмуляцией на x86_64-хосте, точно так же, как бутстрап всей rootfs (README.md §7) и пример `hello` (README.md §15.2).

Если же `abuild -r` запустить прямо на x86_64-хосте без chroot — получится `x86_64`-пакет, для платы бесполезный. Если нужна изоляция получше, чем «просто chroot», есть ещё два варианта:

| Метод | Как | Когда уместен |
|---|---|---|
| **Chroot + qemu** (описан выше) | `sudo chroot $BUILDROOT`, дальше как обычно | Проще всего, ничего дополнительно ставить не нужно — переиспользует README.md §8 |
| **`abuild rootbld`** | `apk add abuild-rootbld`, затем `abuild rootbld` | Более чистая изоляция — сборка в одноразовой bubblewrap-песочнице, а не в уже существующем chroot; тот же qemu/binfmt должен быть настроен в хост-системе |
| **`CBUILD`/`CHOST`/`CTARGET`** | «Настоящее» кросс-компилирование без эмуляции — теми же переменными, которыми сама Alpine собирает свои кросс-тулчейны (`scripts/bootstrap.sh` в aports) | Как правило, не для типовых пакетов: далеко не каждый APKBUILD и не каждая система сборки апстрима умеет корректно кросс-собираться без эмуляции; используйте только если конкретный пакет это явно поддерживает (пример — `./configure --build=$CBUILD --host=$CHOST` для autotools-проектов) |

Для подавляющего большинства собственных пакетов проще и надёжнее первый вариант — именно он используется во всём README.md.

## 7. Подпакеты (-dev, -doc и т.п.)

Если пакет собирает библиотеку, заголовки/статику принято выносить в `-dev`-подпакет, документацию — в `-doc`:

```sh
subpackages="$pkgname-dev $pkgname-doc"
```

Стандартные `-dev`/`-doc`/`-lang` умеют собираться автоматически встроенными функциями abuild (перенос `usr/include`, `usr/lib/*.a`, `usr/share/man` и т.п. — писать код руками часто не нужно). Для нестандартного разбиения — своя функция с именем подпакета:

```sh
subpackages="$pkgname-dev libhello:_lib"

_lib() {
	pkgdesc="$pkgdesc (shared library)"
	amove usr/lib/libhello.so.*
}
```

Внутри функции подпакета доступны `$subpkgname` (имя подпакета) и `$subpkgdir` (куда раскладывать файлы); хелпер `amove` переносит файлы из `$pkgdir` в `$subpkgdir`, создавая недостающие каталоги.

## 8. Публикация и подключение своего репозитория к rootfs

Собранные пакеты нужно физически показать целевой rootfs.

**Локально, тот же хост** — просто указать путь как репозиторий:

```sh
echo "/home/user/packages/aports-local" >> /etc/apk/repositories
```

**По HTTP, для платы или другого компьютера в сети** — раздать каталог веб-сервером и указать URL:

```bash
cd ~/packages/aports-local && python3 -m http.server 8000
```
```sh
echo "http://<ip-хоста>:8000/aports-local" >> /etc/apk/repositories
```

В обоих случаях целевой системе нужен ещё и сам публичный ключ подписи — иначе та же ошибка untrusted, что при bootstrap в README.md §7:

```sh
scp ~/.abuild/*.rsa.pub root@<ip-платы>:/etc/apk/keys/
```

```sh
apk update
apk add hello-zynq
```

## 9. Обновление и пересборка пакета

Изменили исходники, но версия та же — увеличьте `pkgrel` (`0` → `1` и т.д.); обновилась версия апстрима — поменяйте `pkgver` и сбросьте `pkgrel=0`. После любого изменения `source=` контрольные суммы нужно пересчитать заново:

```sh
abuild checksum
abuild -r
```

Старые `.apk` в `REPODEST` не удаляются автоматически — `apk upgrade` на целевой системе сам выберет более новую версию по `pkgver`/`pkgrel`, но подчистить каталог руками при желании можно в любой момент.

## 10. Полезные инструменты

- `newapkbuild -a|-C|-m|-p|-y|-r` — шаблоны под autotools/CMake/meson/perl/python/rust вместо голой заглушки по умолчанию.
- `apkbuild-lint` (пакет `atools`) — проверка APKBUILD на типичные ошибки и несоответствия стилю.
- `abuild -k` — не удалять временные каталоги сборки при ошибке (удобно для отладки `build()`).
- `abuild -f` — форсировать пересборку, даже если готовый `.apk` уже есть.
- `abuild fetch` / `abuild unpack` — только скачать/распаковать источники без сборки (удобно для пошаговой отладки `prepare()`/`build()`).

## 11. Типичные ошибки

| Ошибка | Причина | Решение |
|---|---|---|
| Собранный `.apk` не той архитектуры (`x86_64` вместо `armv7`) | `abuild -r` запущен вне armv7-chroot | Собирать внутри chroot (раздел 3/6); проверить `apk --print-arch` перед сборкой |
| `abuild: you must be a member of group abuild` | Пользователь не добавлен в группу `abuild`, либо не перезашёл после `addgroup` | `addgroup <user> abuild`, затем заново `su - <user>` (групповое членство применяется с нового входа) |
| `UNTRUSTED signature` при `apk add` пакета из своего репозитория | Публичный ключ (`*.rsa.pub`) не скопирован в `/etc/apk/keys` на целевой системе | См. раздел 8 |
| `abuild checksum` не находит файл из `source=` | Файл не лежит рядом с APKBUILD (для локальных источников) либо недоступен URL | Проверить путь/сетевой доступ |
| Сборка виснет или падает под qemu на непонятной инструкции | Редкий артефакт трансляции синтаксисов в qemu-user (не всё транслируется 1:1) | Обновить `qemu-user-static`; в упорных случаях — собрать именно этот пакет на настоящем ARM-железе |
| `abuild -r` не может доустановить `makedepends` | Внутри chroot нет `sudo`/`doas`, либо не настроен | `apk add sudo` (или `doas`) и правило в `/etc/sudoers` (раздел 3) |
