## 1. О документе

Этот документ — самостоятельная тема, не привязанная конкретно к Zynq: обычная сборка `.apk`-пакетов Alpine под архитектуры **armv7** (основной вариант во всём мануале) и **armhf** (полностью аналогично, отличается только имя архитектуры). Пригодится, когда нужной программы нет в `main`/`community`, либо нужна своя версия/патч существующего пакета.

Сборка выполняется на x86_64-хосте через тот же механизм chroot + qemu-user-static, что уже настроен на странице [«Подготовка хоста», раздел 3](Host-Build-Environment.md#3-chroot-окружение-qemu-user-static--binfmt_misc) — внутри ARM-chroot нужны `alpine-sdk` и настроенное повышение прав. Команды ниже рассчитаны на Alpine **3.20** (`abuild` 3.13); на Debian/Ubuntu выполняются только явно обозначенные команды хоста. Это нативная сборка под эмуляцией, не сборка x86_64-бинарника ARM-компилятором.

## 2. Как устроена система пакетов Alpine

- **`apk`** — сам пакетный менеджер: ставит `.apk`, знает про репозитории, подписи, зависимости. С ним уже работали при [настройке rootfs](Rootfs-Build.md#4-настройка-системы-внутри-rootfs) (`apk add`, `apk update`).
- **`abuild`** — инструмент **сборки** пакета из исходников по рецепту `APKBUILD` (аналог `dpkg-buildpackage` у Debian, `makepkg` у Arch, `ebuild` у Gentoo).
- **`aports`** — git-репозиторий, где Alpine хранит APKBUILD-рецепты всех официальных пакетов (`main`, `community`, `testing`): https://gitlab.alpinelinux.org/alpine/aports. Свой пакет оформляется точно так же, просто в собственном каталоге — не обязательно быть частью официального aports.
- **`APKBUILD`** — сам файл-рецепт: shell-скрипт с определённым набором переменных и функций.
- **`alpine-sdk`** — метапакет, который ставит `abuild` и сопутствующие инструменты одной командой.

## 3. Подготовка окружения для сборки

`abuild` должен работать от **обычного пользователя**, а не root — так безопаснее, поскольку сборочные скрипты сторонних пакетов выполняют произвольный код; пользователь должен состоять в группе `abuild`.

Проще всего переиспользовать уже готовый armv7-chroot ([«Сборка rootfs», разделы 2–3](Rootfs-Build.md#2-способ-a-быстрый-старт-с-alpine-minirootfs) и [«Подготовка хоста», раздел 3](Host-Build-Environment.md#3-chroot-окружение-qemu-user-static--binfmt_misc)). Для чистоты можно завести отдельный такой же chroot специально под сборку — чтобы не тащить компиляторы и dev-заголовки в продакшен-rootfs; процедура бутстрапа при этом идентична [«Сборка rootfs», разделы 2/3](Rootfs-Build.md#2-способ-a-быстрый-старт-с-alpine-minirootfs), менять нечего.

```bash
: "${BUILDROOT:?Укажите абсолютный путь к подготовленной ARM-rootfs}"
sudo chroot "$BUILDROOT" /bin/sh
```

Внутри chroot (ещё от root — на этом шаге нужны права на `adduser`/`apk add`):

```sh
apk update
apk add alpine-sdk sudo
adduser -D -s /bin/ash builder
addgroup builder abuild
install -d -m 0750 /etc/sudoers.d
printf '%s\n' 'builder ALL=(ALL) NOPASSWD: ALL' > /etc/sudoers.d/builder
chmod 0440 /etc/sudoers.d/builder
visudo -cf /etc/sudoers.d/builder
su - builder
```

Пользователя создавайте один раз; если `builder` уже существует, не повторяйте `adduser`. Явное `-s /bin/ash` важно: в минимальной rootfs `/bin/bash` может отсутствовать. Правило `NOPASSWD: ALL` допустимо только в отдельном доверенном сборочном окружении: оно даёт сборщику полные права внутри chroot; chroot не является защитной песочницей для чужих APKBUILD. Не добавляйте это правило на рабочую плату.

Дальше всё — уже от имени `builder`. Проверьте архитектуру (`armv7` или `armhf`, не `x86_64`) и один раз сгенерируйте ключ подписи:

```sh
export PATH="/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"
apk --print-arch
SUDO=sudo abuild-keygen -a -i -n
```

`-a` записывает путь к приватному ключу (`PACKAGER_PRIVKEY`) в `~/.abuild/abuild.conf`; `-i` устанавливает **публичный** ключ в `/etc/apk/keys` этой chroot-системы; `-n` использует значения по умолчанию без вопросов. `SUDO=sudo` явно выбирает настроенный выше способ повышения прав. Не генерируйте новые ключи при каждой пересборке.

> Приватный ключ (`~/.abuild/*.rsa`) храните только на доверенных сборочных машинах, с правами `0600` и резервной копией. На плату для установки пакетов передаётся **только** публичный ключ (`*.rsa.pub`). Для нескольких сборщиков можно использовать разные ключи, установив соответствующие публичные ключи на целевые системы.

## 4. Анатомия APKBUILD

Минимальный, но полный пример — тот же `hello.c`, что и в [«Кросс-компиляция», раздел 2](Cross-Compilation.md#2-способ-a-сборка-внутри-chroot), только теперь оформленный как настоящий `.apk`-пакет вместо разовой ручной установки файла:

```sh
# Contributor: Ваше Имя <you@example.com>
# Maintainer: Ваше Имя <you@example.com>
pkgname=hello-zynq
pkgver=1.0
pkgrel=0
pkgdesc="Тестовая программа для Zynq-7010"
url="https://example.com/"
arch="all"
license="MIT"
depends=""
makedepends=""
subpackages=""
source="hello.c"
builddir="$srcdir"

build() {
	cd "$builddir"
	${CC:-cc} $CFLAGS $CPPFLAGS -o hello hello.c $LDFLAGS
}

check() {
	cd "$builddir"
	[ "$(./hello)" = "Hello, Zynq!" ]
}

package() {
	cd "$builddir"
	install -Dm755 hello "$pkgdir"/usr/bin/hello
}

sha512sums=""
```

Разбор ключевых полей:

| Поле/функция | Назначение |
|---|---|
| `pkgname`, `pkgver`, `pkgrel` | Имя, версия, номер пересборки (увеличивайте `pkgrel`, если меняли APKBUILD без смены `pkgver`) |
| `arch` | `all` — рецепт можно собрать под любую архитектуру (каждый раз получится свой arch-специфичный `.apk`, это не «универсальный бинарник»); `noarch` — по-настоящему не зависящий от архитектуры контент (скрипты, данные); либо явный список `"armv7 armhf aarch64"` |
| `depends` | Зависимости времени выполнения — ставятся вместе с пакетом на целевой машине |
| `makedepends` | Зависимости только для сборки, в готовый пакет не попадают |
| `source` | Список источников: URL, либо, как в примере, просто имя локального файла рядом с APKBUILD (раз имя не похоже на URL — abuild берёт файл локально, не пытаясь скачать) |
| `build()` | Компиляция; рабочий каталог — `$builddir` (для архивов обычно `$srcdir/<имя-версия>` после распаковки) |
| `check()` | Тесты; `abuild -r` выполняет их. Если пакет действительно не имеет тестов, явно задайте `options="!check"` и объясните причину. `-k` тесты **не** отключает |
| `package()` | Раскладка готовых файлов в `$pkgdir` — именно это содержимое попадёт в `.apk` |
| `sha512sums` | Контрольные суммы всех файлов из `source=`; на практике заполняются автоматически командой `abuild checksum`, а не руками |

## 5. Первый пакет: от newapkbuild до готового .apk

Каркас можно сгенерировать `newapkbuild`. Команда сама создаёт каталог `hello-zynq`, поэтому запускайте её из **родительского** каталога, не из заранее созданного каталога пакета:

```sh
mkdir -p ~/aports-local
cd ~/aports-local
newapkbuild -d "Тестовая программа для Zynq-7010" -l MIT hello-zynq-1.0
cd hello-zynq
cat > hello.c <<'EOF'
#include <stdio.h>

int main(void)
{
    puts("Hello, Zynq!");
    return 0;
}
EOF
```

`newapkbuild` создаст шаблон `APKBUILD` — отредактируйте его по образцу раздела 4; `build()`/`package()` под конкретную программу почти всегда приходится дописывать руками, автогенерация закрывает только каркас (а для типовых систем сборки есть готовые шаблоны — `newapkbuild -a` для autotools, `-C` для CMake, `-m` для meson, `-y` для python, `-r` для rust).

Если каталог уже существует, не запускайте генератор повторно и не используйте `-f` без проверки: он может перезаписать рецепт. Флаг `-n` в `newapkbuild` допускается только при последнем аргументе **URL исходников**, а не `hello-zynq-1.0`.

Замените содержимое созданного `APKBUILD` полным рецептом из раздела 4 (уберите шаблонный URL архива; оставьте `source="hello.c"`). Пустой `sha512sums` — место для автоматически вычисляемой суммы, а не готовая контрольная сумма. Затем:

```sh
abuild checksum
abuild -r
```

`abuild checksum` запишет актуальный `sha512sums=` для фактического содержимого `hello.c`. `abuild -r` устанавливает сборочные зависимости через `SUDO_APK` (по умолчанию `abuild-apk` из `abuild-sudo`, установленного вместе с `alpine-sdk`), выполняет тесты и создаёт подписанные пакет и `APKINDEX.tar.gz`. Поля `CFLAGS`/`CPPFLAGS`/`LDFLAGS` сохраняют стандартные флаги Alpine. Для пакетного менеджера программа установлена в `/usr/bin`, а не в `/usr/local/bin`, предназначенный для ручных установок.

Готовый файл окажется в `~/packages/<репозиторий>/<arch>/hello-zynq-1.0-r0.apk` — имя репозитория берётся из непосредственного родительского каталога каталога пакета (в примере — `aports-local`), путь настраивается переменной `REPODEST` в `~/.abuild/abuild.conf` или `/etc/abuild.conf`.

## 6. Кросс-архитектурная сборка: armv7/armhf на x86_64-хосте

Если разделы 3–5 выполнялись **внутри** armv7-chroot (как и рекомендовано) — всё уже собралось под правильную архитектуру, отдельно ничего делать не нужно: `apk --print-arch` внутри такого chroot и так вернёт `armv7`, и `abuild` соберёт пакет «нативно» с точки зрения инструментов — хотя физически всё выполняется под qemu-эмуляцией на x86_64-хосте, точно так же, как бутстрап всей rootfs ([«Сборка rootfs», раздел 3](Rootfs-Build.md#3-способ-b-сборка-rootfs-с-нуля-через-apk-tools-static)) и пример `hello` ([«Кросс-компиляция», раздел 2](Cross-Compilation.md#2-способ-a-сборка-внутри-chroot)).

Если же `abuild -r` запустить прямо на x86_64-хосте без chroot — получится `x86_64`-пакет, для платы бесполезный. Если нужна изоляция получше, чем «просто chroot», есть ещё два варианта:

| Метод | Как | Когда уместен |
|---|---|---|
| **Chroot + qemu** (описан выше) | `sudo chroot "$BUILDROOT" /bin/sh`, дальше как обычно | Проще всего, ничего дополнительно ставить не нужно — переиспользует [«Подготовка хоста», раздел 3](Host-Build-Environment.md#3-chroot-окружение-qemu-user-static--binfmt_misc) |
| **`abuild rootbld`** | `apk add abuild-rootbld`, затем `abuild rootbld` | Отдельный продвинутый вариант: нужен Alpine-хост, поддержка user namespaces/bubblewrap и доступ к репозиториям. Это не автоматический переключатель x86_64 → ARM: обычный запуск на x86_64 собирает x86_64; для ARM нужны ARM-среда и корректная настройка qemu/binfmt. В некоторых контейнерах и chroot rootbld недоступен |
| **`CBUILD`/`CHOST`/`CTARGET`** | «Настоящее» кросс-компилирование без эмуляции — теми же переменными, которыми сама Alpine собирает свои кросс-тулчейны (`scripts/bootstrap.sh` в aports) | Как правило, не для типовых пакетов: далеко не каждый APKBUILD и не каждая система сборки апстрима умеет корректно кросс-собираться без эмуляции; используйте только если конкретный пакет это явно поддерживает (пример — `./configure --build=$CBUILD --host=$CHOST` для autotools-проектов) |

Для подавляющего большинства собственных пакетов проще и надёжнее первый вариант — именно он используется во всём мануале.

## 7. Подпакеты (-dev, -doc и т.п.)

Если пакет собирает библиотеку, заголовки/статику принято выносить в `-dev`-подпакет, документацию — в `-doc`:

```sh
subpackages="$pkgname-dev $pkgname-doc"
```

Стандартные `-dev`/`-doc`/`-lang` используют встроенные функции abuild. `-dev` обычно забирает заголовки, pkg-config и незаверсионированные `.so`; статические `.a` оформляют отдельно через `$pkgname-static`. `-doc` забирает документацию. Указывайте только подпакеты, для которых действительно есть файлы. Пример ниже относится к **библиотеке**, не к `hello-zynq`: для него нужны реальный `package()`, устанавливающий `.so` и заголовки, и собственная функция разделения:

```sh
subpackages="$pkgname-dev libhello:_lib"

_lib() {
	pkgdesc="$pkgdesc (shared library)"
	amove usr/lib/libhello.so.*
}
```

Внутри функции подпакета доступны `$subpkgname` (имя подпакета) и `$subpkgdir` (куда раскладывать файлы); хелпер `amove` переносит файлы из `$pkgdir` в `$subpkgdir`, создавая недостающие каталоги.

## 8. Публикация и подключение своего репозитория к rootfs

Сборщик создаёт структуру `~/packages/aports-local/<arch>/`, содержащую `.apk` и подписанный `APKINDEX.tar.gz`. В `/etc/apk/repositories` указывают **родительский** каталог архитектуры; `apk` сам добавляет `armv7` или `armhf`.

### Локально: внутри той же сборочной chroot

Выйдите из `su - builder` командой `exit` и выполните от root **в этой chroot**:

```sh
repo=/home/builder/packages/aports-local
grep -qxF "$repo" /etc/apk/repositories || printf '%s\n' "$repo" >> /etc/apk/repositories
apk update
apk add hello-zynq
hello
```

Публичный ключ здесь уже установлен через `abuild-keygen -i`. Другая rootfs не видит каталоги хоста автоматически: скопируйте репозиторий внутрь неё или смонтируйте его туда. На реальной плате путь `/home/builder/...` хоста не работает.

### По HTTP: для платы или другой rootfs

На машине, **где доступны собранные пакеты**, установите Python 3 (в Alpine: `apk add python3`, от root). Если пакеты внутри chroot, запускайте сервер там от `builder` либо заранее скопируйте их на хост:

```sh
python3 -m http.server 8000 --bind 0.0.0.0 --directory "$HOME/packages/aports-local"
```

Сервер занимает терминал; дальнейшие команды выполняйте в другом. Он раздаёт только этот каталог. Ограничьте доступ доверенной локальной сетью; для постоянной публикации используйте HTTPS. Корень HTTP уже соответствует `aports-local`, поэтому добавлять `/aports-local` к URL **не нужно**.

Передайте публичный ключ на плату. Ниже адрес `192.168.1.50` — пример, замените его; команда выполняется от `builder` там, где находится ключ. Нужны SSH-клиент (`apk add openssh-client`, от root) и настроенный SSH-доступ к плате:

```sh
BOARD_IP=192.168.1.50
scp "$HOME"/.abuild/*.rsa.pub "root@$BOARD_IP:/etc/apk/keys/"
```

Если ключ остался внутри chroot, а `scp` запускаете на хосте, сначала скопируйте **публичный** файл наружу. Приватный ключ передавать на плату не нужно. На плате (root) добавьте адрес **сервера**, например `192.168.1.10`, а не адрес самой платы:

```sh
REPO_HOST=192.168.1.10
repo="http://$REPO_HOST:8000"
grep -qxF "$repo" /etc/apk/repositories || printf '%s\n' "$repo" >> /etc/apk/repositories
apk update
apk add hello-zynq
hello
```

Для `armv7` индекс должен быть доступен как `http://192.168.1.10:8000/armv7/APKINDEX.tar.gz`. Пакет, репозитории зависимостей и целевая система должны иметь совместимые архитектуру и ветку Alpine 3.20. Не обходите проверку подписи через `--allow-untrusted`.

## 9. Обновление и пересборка пакета

Изменили исходники, но версия та же — увеличьте `pkgrel` (`0` → `1` и т.д.); обновилась версия апстрима — поменяйте `pkgver` и сбросьте `pkgrel=0`. После изменения списка `source=` **или содержимого любого исходного файла**, включая локальный `hello.c`, пересчитайте суммы:

```sh
abuild checksum
abuild -r
```

Старые `.apk` при обычной сборке остаются в `REPODEST`. Для удаления старых версий **текущего рецепта** выполните `abuild cleanoldpkg` из его каталога: команда оставит текущую версию и обновит подписанный индекс. Не удаляйте пакеты, которые нужны для отката. Если удаляете `.apk` вручную, затем выполните `abuild index`, чтобы индекс не ссылался на отсутствующие файлы.

На целевой системе (root):

```sh
apk update
apk upgrade hello-zynq
hello
```

## 10. Полезные инструменты

- `newapkbuild -h` — список доступных шаблонов; выбирайте **один** флаг: `-a` autotools, `-C` CMake, `-m` Meson, `-p` Perl, `-y` Python setuptools, `-e` Python gpep517, `-r` Rust. Запись с `|` не является командой для копирования.
- `apkbuild-lint APKBUILD` (пакет `atools`, установить от root: `apk add atools`) — проверка рецепта; запускайте от сборщика из каталога пакета.
- `abuild -r -K` — сохранить временные каталоги и сборочные зависимости. Маленькая `-k` означает другое: не пересобирать уже существующие пакеты, даже если рецепт или исходники новее. Ни `-k`, ни `-K` не отключают `check()`.
- `abuild -f` — форсировать пересборку, даже если готовый `.apk` уже есть.
- `abuild fetch verify unpack` — получить исходники, проверить контрольные суммы и распаковать без полной сборки; для патчей затем `abuild prepare`. Сам по себе `fetch` не заменяет проверку подписи/контрольных сумм.

## 11. Типичные ошибки

| Ошибка | Причина | Решение |
|---|---|---|
| Собранный `.apk` не той архитектуры (`x86_64` вместо `armv7`) | `abuild -r` запущен вне armv7-chroot | Собирать внутри chroot (раздел 3/6); проверить `apk --print-arch` перед сборкой |
| `abuild: you must be a member of group abuild` | Пользователь не добавлен в группу `abuild`, либо не перезашёл после `addgroup` | `addgroup <user> abuild`, затем заново `su - <user>` (групповое членство применяется с нового входа) |
| `UNTRUSTED signature` при `apk add` пакета из своего репозитория | Публичный ключ (`*.rsa.pub`) не скопирован в `/etc/apk/keys` на целевой системе | См. раздел 8 |
| `abuild checksum` не находит файл из `source=` | Файл не лежит рядом с APKBUILD (для локальных источников) либо недоступен URL | Проверить путь/сетевой доступ |
| Сборка виснет или падает под qemu на непонятной инструкции | Редкий артефакт трансляции синтаксисов в qemu-user (не всё транслируется 1:1) | Обновить `qemu-user-static`; в упорных случаях — собрать именно этот пакет на настоящем ARM-железе |
| `abuild -r` не может доустановить `makedepends` | Нет `abuild-apk`, пользователь не в группе `abuild`, неверно задан `SUDO_APK`, либо недоступны репозитории | Проверить `alpine-sdk`/`abuild-sudo`, `id`, `apk update`; затем повторно войти через `su - builder` |
| `su: can't execute /bin/bash` | Пользователю назначена отсутствующая оболочка | Создавать через `adduser -D -s /bin/ash builder`; для существующего пользователя root может исправить запись в `/etc/passwd` |
| `-n is only allowed when using SRCURL` | `newapkbuild -n` вызван с именем вместо URL | Использовать команду из раздела 5 без `-n` |
| HTTP-репозиторий возвращает 404 | URL не соответствует корню сервера либо нет каталога нужной архитектуры/индекса | Проверить адрес `/<arch>/APKINDEX.tar.gz` и раздел 8 |

### Проверка примера

Команды проверены 2026-10-11 в отдельных rootfs Alpine 3.20 с `abuild 3.13.0-r3`:

- **armv7 и armhf, QEMU:** создание пользователя, ключей, шаблона и исходника; `abuild checksum`, сборка с `check()`, подписанный индекс, установка из локального репозитория и запуск `hello`.
- **x86_64:** дополнительно установка через HTTP и обновление `1.0-r0` → `1.0-r1`.
- Все 14 блоков shell-команд прошли синтаксическую проверку `sh -n`.

Это не проверка на физической Zynq-плате. Передача через SSH на конкретную плату, `rootbld`, настоящий cross-toolchain и библиотечные подпакеты зависят от внешнего окружения/проекта и не проходили здесь полный end-to-end тест. При первой сборке предупреждение об отсутствующем ещё каталоге `~/packages/aports-local` допустимо: abuild создаёт его при публикации пакета.
